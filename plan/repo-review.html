Repo review, method, and what changed

The repo arrived with eight prior sessions' work and four parallel dashboards. This page records the audit, how this surface sits beside the existing root dashboard without colliding with it, and how the build enforces its own claims.

Method

  • Read the official page, then its document. Event rows come from the DSE IV schedule page; fee, stack, level, registration and guarantee come from that event's structure sheet. Buy-ins and guarantees parsed from the event name are cross-checked against the sheet text, and a mismatch aborts the build.
  • Three states, never two. explicit (the source says it, excerpt stored), not stated after a full read (we read it and the clause is absent), not read (no claim). Only the first two may appear in a table, and only a full read with a confirmed fee and guarantee may be ranked.
  • Computed values are labelled computed. Ratios and “earliest plausible finish” are derived from published times; the derivation is printed next to the table so nobody reads it as a scheduled end time.
  • No outbound network in the build sandbox (GitHub, npm and PyPI only), so live re-reads happen in the GitHub Actions job, which reports here rather than silently rewriting data.

Irregularities found in the repo itself

  • FG-14: data/tournaments.json attributed structure-sheet values (registration cutoff, stack, level length) to the schedule page, and a second session had already flagged those fields as unreproducible from that page. Both were half right: the values are real, the attribution was not. Fixed by per-field source links in the new dataset.
  • FG-15: data/venetian-dse4-official-check.json (47 rows) and data/verified/tournaments.json (32 rows) each labelled rows “single_entry” on sheet silence alone, and the former counted per-flight rows as separate single-entry events. The consolidated dataset uses three states and groups flights by event.
  • FG-16: Four front-ends (the repository root dashboard, /docs/, /verified/, /pages/) render four datasets with different labels for the same event. Nothing was deleted to fix that: the root dashboard belongs to scripts/build_site.py and its CI ownership note, and this /plan/ surface is generated beside it from site-data/*.json. Consolidating to one surface is suggestion S-11.
  • FG-19: For every Venetian row whose sheet was read (all of them as of 2026-11-17), the buy-in is fee-inclusive: fee + prize pool equals the published buy-in, which the build checks. Other-venue rows that have no read sheet keep the published buy-in with a caveat instead of a computed total.
  • Repo hygiene: The root carries style.css, styles.css, app.js and assets/ from several sessions with overlapping selectors. All of them stay in place because the root dashboard references them; this surface ships its own plan/assets/site.css and plan/assets/site.js, and the build fails if either is missing, so neither page set can restyle the other.
