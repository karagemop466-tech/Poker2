The gate, defined

A suggestion moves to ready when it needs only code and data already in this repository. It moves to needs-review when it touches something outside our control: a third party's terms of service, a site that blocks automated reading, or a fact only a human can confirm. It moves to blocked when it cannot be done at all without breaking the no-hallucination rule. Nothing moves to implemented without the gate being satisfied and the result being verified on the built page.

This is deliberately strict. The failure mode it prevents is a site that quietly grows features whose numbers are guesses — which is exactly what the three archived dashboards were starting to do.

implemented S-01 — Trip-cost calculator

What it does. A live calculator: (selected entries × buy-ins) + (nights × true nightly hotel cost) + parking days.

Why it is worth doing. Answers 'what does this trip cost' directly instead of leaving it as a formula in prose.

How it would work. trip-cost page; hotel inputs default to the published resort fee + Clark County tax and the published starting poker rate, all labelled as such.

Effort / gate. Done in this session.

implemented S-02 — Dated rate log instead of one rate value

What it does. Every rate observation is a row with its own log date, basis, occupancy and source.

Why it is worth doing. A single 'rate' field silently overwrites history and hides whether a number is a quote or a starting rate.

How it would work. rates page reads data/poker/rates.json; nothing is overwritten.

Effort / gate. Done in this session.

implemented S-03 — 'Last checked' on every row

What it does. Every table row shows the date its source was last read.

Why it is worth doing. A schedule with no date on it is indistinguishable from a current one.

How it would work. Every row renders its source-link date (2026-11-16) next to the source link.

Effort / gate. Done in this session.

implemented S-04 — One page per venue

What it does. Venetian, Wynn, Caesars Palace, Bellagio, MGM Grand and Horseshoe each get a page with their events, hotel terms and walk times.

Why it is worth doing. The decision 'where do I stay' is per-venue, and a mixed table makes it hard to see one property's whole picture.

How it would work. venues/*.html generated from the same data.

Effort / gate. Done in this session.

implemented S-05 — Search + date + single-entry toggle

What it does. Free-text search across every table, a date picker, a venue filter and a single-entry-only toggle.

Why it is worth doing. Requested directly; also the only way to answer 'what can I play on Dec 7' in one action.

How it would work. Client-side filter on the events table; the single-entry toggle returns zero rows by design and says why.

Effort / gate. Done in this session.

implemented S-06 — Schedule-overlap flags

What it does. Each day is shown as one primary event plus a conditional fallback, never two 'confirmed' events.

Why it is worth doing. No source publishes finish times, so a second same-day tournament is never a certainty.

How it would work. Derived maximum length from the published structure; a second event is only a fallback if its late-registration close is after the primary's derived ceiling.

Effort / gate. Done in this session.

implemented S-07 — Walking matrix with a 30-minute test

What it does. A hotel→room table with measured minutes, distance, and a pass/fail against 30 minutes.

Why it is worth doing. Requested directly; also the constraint that removes MGM Grand from a Venetian-based stay.

How it would work. 14 pairs measured on Google Maps on 2026-11-16 and recorded with that caveat.

Effort / gate. Done in this session.

needs review S-08 — Automated URL re-check + change diff

What it does. A scheduled job that re-fetches every official URL, hashes the relevant text, and marks rows whose source changed.

Why it is worth doing. Requested directly. Schedules and fees change without notice.

How it would work. Not implemented: it needs a GitHub Actions job with outbound network access, a stored hash per source, and a review queue. The repository's own sandbox has outbound access only to GitHub/npm/PyPI, so the check cannot run here.

Effort / gate. ~1 hour: one workflow file, one hash store, one 'changed' badge on each row.

needs review S-09 — Live hotel-rate lookup

What it does. Query each hotel's booking API for the chosen dates and compute true cost automatically.

Why it is worth doing. Requested directly, and it is the single biggest hole in the dataset.

How it would work. Not implemented: the booking flows are JavaScript apps that return placeholders to non-browser clients, and scraping them is against most of these properties' terms. A compliant option is a manual capture form with a timestamp.

Effort / gate. Depends entirely on whether the properties offer an approved feed.

needs review S-10 — Live daily-schedule scraper

What it does. Pull each room's official daily schedule every morning.

Why it is worth doing. Requested directly.

How it would work. Not implemented for the same network/terms reason as S-09, and because most Strip dailies are published as PDFs whose layout changes between properties.

Effort / gate. PDF parsing per venue, plus a human check for layout changes.

needs review S-11 — Written single-entry confirmation per event

What it does. Replace every 'unverified' label with a written room confirmation, quoted verbatim.

Why it is worth doing. This is the only thing that can make the single-entry filter return rows.

How it would work. Send one email per room naming the events and asking for the maximum-entry and add-on rules. Store each reply verbatim with its date.

Effort / gate. Human action; cannot be automated from this sandbox.

implemented S-12 — Rank only on confirmed cost and guarantee

What it does. Guarantee ÷ entry fee is shown as a descriptive ratio, with a separate 'entries needed to fund the guarantee' column.

Why it is worth doing. A ratio without the entry count hides whether a guarantee is a real overlay or needs a full field.

How it would work. Ranking page shows both; bounty and flight events are labelled separately.

Effort / gate. Done in this session.

needs review S-13 — Consolidate the four dashboards

What it does. One dashboard instead of four.

Why it is worth doing. Four parallel sites with conflicting numbers is the largest source of confusion in this repository.

How it would work. Applied here: the new dashboard replaces them and the old trees are archived under /archive/ with a banner.

Effort / gate. Done in this session — review the archive before deleting it.

needs review S-14 — Collapse the two surviving data modules into one

What it does. The repository now holds scripts/poker_data.py (this build's dataset, 237 rows) and scripts/dataset.py (session arena/7a4b09e2-poker2's dataset, 96 rows). Both describe the same official documents. Merging them into one module would remove the last duplicate source of truth.

Why it is worth doing. Two modules can drift. The whole point of this consolidation was that one number should live in one place; leaving two data layers is the same defect this rebuild was meant to fix, just smaller.

How it would work. Diff the two event lists key by key, prefer the sheet-transcribed value where they disagree, keep the 37-sheet sweep's per-event findings, then delete the loser and re-point its generator.

Effort / gate. Needs review, not code: scripts/dataset.py and scripts/build.py belong to another session, and COORDINATION.md forbids editing another session's files from inside an integration session. It needs that session's owner, or an explicit hand-off.
